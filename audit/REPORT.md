## 4. Findings

### H-01 Daily reward array uses Unix-day indexes without an epoch offset

Severity: High
Impact: A matured stake cannot be ended while `dailyData.length` is not greater than its Unix `endDayIndex`; the caller's `stakeEnd` transaction reverts before the stake is cleared or payout minted. This blocks the normal claim path for deposited principal under the tested schedule.
Likelihood: High when the owner/keeper appends only current-period daily records, because array index zero is treated as Unix day zero. Repair requires appending all preceding daily rows or changing the indexing model.
Confidence: High
Calibration: [VERIFIED: PoC executed + output]
SCWE: SCWE-083 (general edge-case classification; the bundled description includes state-dependent logic and boundary failures, not this exact timestamp-to-array-index pattern); [SCWE-083](https://scs.owasp.org/SCWE/SCSVS-COMP/SCWE-083/).
SCSVS: SCSVS-GOV-3 (logic and transaction-flow integrity), SCSVS-BLOCK-1 (gas and resource constraints); [SCSVS-GOV-3](https://scs.owasp.org/SCSVS/controls/SCSVS-GOV-3/), [SCSVS-BLOCK-1](https://scs.owasp.org/SCSVS/controls/SCSVS-BLOCK-1/), [SC03:2025 Logic Errors](https://scs.owasp.org/sctop10/archive/2025/SC03-LogicErrors/).
Locations: `contracts/SynergiXStaking.sol:215-224` uses `block.timestamp`-derived day indexes as direct array indexes and checks only `endDayIndex < dailyData.length`; `contracts/SynergiXStaking.sol:406-414` appends a single row and exposes no epoch offset, explicit day index, or batch backfill. Claim entry point: `contracts/SynergiXStaking.sol:145-152`; token forwarding: `contracts/SynergiXToken.sol:114-121`.
Root cause: The daily series' zero-based append index is assumed to equal the number of days since Unix epoch. The code does not align index zero to deployment/start day or provide an initialization/offset mechanism.
Attack scenario:
1. Actor: ordinary staker; prerequisite: approve and stake the required principal through `SynergiXToken.stake`, with no special timing or capital beyond the normal stake.
2. The owner/keeper appends a current daily record through `addDailyData`; array length is one while current Unix day indexes are much larger.
3. After maturity, the staker calls `SynergiXToken.stakeEnd`; `_calculatePayout` reverts at the end-day length check, leaving the stake active and payout unavailable.
PoC: EXECUTED `node scripts/hardhat.js test test/poc/H-01.test.js` — exit 0, 1 passing; output assertion observes `Invalid end day index.` on the matured claim. Local Hardhat only; no live system calls. Related documented test: [SCSTG-TEST-0015](https://scs.owasp.org/SCSTG/tests/SCSVS-GOV/SCSTG-TEST-0015/).
Falsification: The strongest counterargument is that the owner can prepopulate every historical day row, or a keeper may already do so. The code permits sequential single-row backfill, so this is not mathematically irreversible. However, there is no batch setter or base-day offset, and the PoC confirms that ordinary current-only appends make claims revert. The complementary local test `node scripts/hardhat.js --config hardhat.epoch.config.js test test/poc/positive-payout.test.js` passes when rows 0 and 1 are present, confirming the index gap is the failure condition. No deployment-specific prepopulated schedule was supplied.
Impact detail: Affected operation is maturity claim/payout. No token loss amount is estimated because tokenomics and deployed state are unknown. Backfill cost is not estimated; the code exposes one `addDailyData` append per transaction and no bulk path.
Recommendation: Index daily data relative to an explicit stored base day, or accept and validate explicit day indexes in a mapping. Define initialization and missing-day behavior; add boundary tests for first day, current day, gaps, and matured claims.
Regression risk: Changing the index model can alter existing reward histories and proxy storage assumptions; validate any deployed history and intended daily accounting before migration.
Status: OPEN

The admin role controls trusted-contract configuration at lines 125-138, role administration at lines 163-172, and UUPS authorization at lines 84-86. Inherited `AccessControl.grantRole`/`revokeRole` remain available to the staking default admin. Ownership transfer therefore does not by itself transfer the default-admin role. The owner can also set `maxStakeDays` to 0 or 1 (`contracts/SynergiXStaking.sol:353-356`), which prevents new stakes because `stakeStart` rejects durations when zero or `calcStakeShares` divides by zero when one (`contracts/SynergiXStaking.sol:113-115, 177-179`); a local test confirms this owner-only misconfiguration and the owner can restore a valid value. Compromise or misconfiguration of trusted roles can alter upgrades, mint authority, settings, referral assignment, and reward schedules. These are architectural trust dependencies; actual role holders, multisig, timelock, and deployed configuration are unknown.

## 7. Discarded candidates

- **Possible stranded principal or inflationary maturity payout — unverified semantics.** `stakeStart` transfers `stakeValue` from the staker into the staking contract (`contracts/SynergiXStaking.sol:116-118`). `stakeEnd` closes the record and mints `payout` to the staker without transferring the stored principal (`contracts/SynergiXStaking.sol:150-166`). The aligned payout test confirms the user receives minted principal plus configured interest while original principal remains in staking. The user confirmed payout intent is unknown; this may be the intended inflationary model, so no loss or severity is asserted.
- **Owner-supplied zero reward denominator — tested privileged schedule hazard, not a permissionless finding.** `_calculatePayout` divides by `dailyData[endDayIndex].totalSShares` (`contracts/SynergiXStaking.sol:219-224`); `addDailyData` accepts zero without validation (`contracts/SynergiXStaking.sol:406-414`). The epoch-configured `test/poc/positive-payout.test.js` reproduces panic `0x12` for a matured claim when the owner supplies a zero end-day total. The append-only row cannot be edited through current functions. The strongest counterargument is that only the trusted owner supplies the schedule; this is an operator/data-integrity hazard, not an unprivileged exploit.
- **Owner can disable new stakes with `maxStakeDays` 0 or 1 — privileged configuration hazard, not a permissionless finding.** The setter accepts both values (`contracts/SynergiXStaking.sol:353-356`); zero makes every positive stake duration invalid, and one makes `calcStakeShares` divide by zero (`contracts/SynergiXStaking.sol:113-115, 177-179`). `test/poc/settings-edge-validation.test.js` reproduced both failures after an owner change. Strongest counterargument: only the trusted owner can change the value and can restore a valid value; the consequence is reversible denial of new staking, so it is treated as a centralization/configuration risk rather than a vulnerability finding.
- **Public staking accepts only exactly 1,000,000 SNX — [INFERRED: code-path reasoning], product intent unknown.** `MAX_STAKING_VALUE` is 1,000,000 SNX (`contracts/SynergiXToken.sol:33-34`) while `MIN_STAKE_VALUE` is the same amount (`contracts/SynergiXStaking.sol:28`); the public token wrapper enforces the upper bound (`contracts/SynergiXToken.sol:96-99`) and staking enforces the lower bound (`contracts/SynergiXStaking.sol:113-115`). Thus any amount above the minimum, including the documented 150,000,000 SNX bonus threshold, is unreachable through `SynergiXToken.stake`. `test/poc/stake-cap-validation.test.js` confirms a minimum stake succeeds and minimum plus one wei reverts. Strongest counterargument: a fixed-size stake may be intentional; no product specification was supplied. This is recorded as a functional constraint, not a security finding.
- **Uninitialized UUPS implementation — tested false positive for proxy takeover.** The implementation has no constructor call to `_disableInitializers`, so an attacker can initialize the standalone implementation and obtain roles in its own storage (`contracts/SynergiXToken.sol:51-71`). `test/poc/upgrade-validation.test.js` confirms the attacker’s direct `upgradeTo` fails the installed UUPS `onlyProxy` guard and leaves the proxy implementation and roles unchanged. This is a defense-in-depth gap (local OWASP reference [SCWE-092](https://scs.owasp.org/SCWE/SCSVS-CODE/SCWE-092/)), not a demonstrated proxy takeover for the installed OpenZeppelin UUPS implementation. Reassess if proxy pattern or upgrade hooks change.
- **Recovered source/build defects — repaired in the working tree, not a security finding.** The duplicate token declaration, initializer imports, undeclared token state/events, and staking token interface mismatch were repaired. The follow-up compile passed as recorded in the appendix; behavioral and security correctness remain outside what that result establishes.
