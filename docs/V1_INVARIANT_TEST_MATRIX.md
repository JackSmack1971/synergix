# SynergiX V1 Invariant Test Matrix

**Status:** PROPOSED test plan; Phase 1 hold remains active.
**Scope:** Test design only. No test code was added or run for this matrix, and no production contract behavior is authorized by it.

This matrix maps the economic criteria in [`V1_TOKENOMICS_DECISION_RECORD.md`](V1_TOKENOMICS_DECISION_RECORD.md) and security invariants grounded in [`audit/REPORT.md`](../audit/REPORT.md) to unit, integration, property-based, and adversarial test requirements. It separates tests that can characterize current behavior from assertions that depend on owner decisions or future V1 implementation. Current legacy test and source-repair evidence is recorded in [`SECURITY_REMEDIATION_STATUS_2026-10-24.md`](SECURITY_REMEDIATION_STATUS_2026-10-24.md); this matrix does not mark unresolved V1 criteria as passed.

## Decision labels

- **NOW-CHAR:** Can be implemented now as a characterization of current legacy behavior. It must be labeled legacy evidence and cannot be presented as proof of the V1 design.
- **NOW-SEC:** A generic security property can be tested against the current interfaces and behavior without selecting economic terms.
- **HYBRID:** Baseline or generic checks can run now; the complete V1 oracle waits for owner decisions or implementation.
- **WAIT-ECON:** The expected result depends on unresolved supply, reward, referral, stake, or exit decisions.
- **WAIT-ADMIN:** The expected result depends on the owner-approved roles, mutable settings, governance, or emergency policy.
- **WAIT-IMPL:** The principle is approved, but current contracts do not implement the V1 behavior. Tests can be authored as specifications; they cannot pass against current legacy semantics.

All `WAIT-*` entries remain behind the Phase 1 hold. A test that intentionally exposes a current defect or behavior must retain its current-state label; do not weaken or relabel it to make the V1 suite appear green.

## Economic invariant matrix

| ID / invariant | Unit tests | Integration tests | Property-based tests | Adversarial tests | Lane |
|---|---|---|---|---|---|
| ECON-01 — Escrowed principal covers aggregate outstanding principal liability. | For each accepted stake, check principal transfer and the corresponding liability update. | Multiple users stake, mature, and withdraw; reconcile contract balance and aggregate open positions after each action. | Generate action sequences and assert `principalAssetsHeld >= outstandingPrincipalLiability` after every successful transition. | Reenter or force token-transfer failure around deposit/withdrawal; assert no undercollateralized or partially updated state. | **HYBRID.** Single-stake escrow characterization exists now; the V1 aggregate invariant requires the V1 liability model and implementation. |
| ECON-02 — A position's principal is returned at most once. | Test maturity boundary, one successful return, then repeat-call rejection with unchanged state. | Exercise multiple positions and users, including duplicate, stale, and cross-user position indexes. | Generate withdrawal/claim sequences and assert each position's cumulative returned principal is at most its recorded principal. | Race same-position calls and attempt unauthorized or reentrant second returns. | **HYBRID.** Legacy duplicate-claim case passes in the epoch-aligned supplemental run; V1 principal-return behavior awaits implementation. |
| ECON-03 — Funded rewards cover all reserved, accrued, and claimable base and referral liabilities. | Check each reserve, accrual, claim, and release update against an independent arithmetic model. | Fund, open concurrent positions, accrue, claim, and close; compare reserve assets with aggregate liabilities. | Generate deposits, funding, accrual, and claims; assert available reserve never becomes negative. | Attempt simultaneous claims, duplicated accrual, referral expansion, and reserve depletion at exact boundaries. | **WAIT-ECON.** Reserve asset, reward formula, referral treatment, rounding, and reservation accounting are open. |
| ECON-04 — Reward payments cannot consume assets owed as principal. | Assert reward payout decreases only reward-reserve accounting. | Interleave principal deposits/withdrawals and reward funding/claims; reconcile separate liabilities. | Across arbitrary action sequences, assert principal coverage remains true after every reward payout. | Attempt to route rewards through principal balances or exploit shared-balance accounting. | **WAIT-ECON.** Separate reserve accounting and payout mechanics are not implemented; full invariant needs approved reward model. |
| ECON-05 — A new commitment is rejected atomically unless its maximum reward liability is fully reserved. | Test exact reserve sufficiency and one smallest unit below the requirement. | Submit accepted and rejected stakes around reserve exhaustion; check all balances, positions, and liabilities. | Generate reserve and commitment amounts; assert accepted commitments are covered and rejected calls preserve state. | Front-run or bundle commitments against the last available reserve; retry after competing claims. | **WAIT-ECON.** Maximum liability, formula, rounding, referral component, and commitment timing are open. |
| ECON-06 — Reward-reserve exhaustion cannot block an otherwise valid matured principal withdrawal. | With reward availability at zero, mature and withdraw a position with no reward claim. | Exhaust reserve across users, then withdraw matured principal while claims are unavailable. | Generate reserve depletion and maturity orderings; assert valid principal exits remain enabled. | Attempt to grief withdrawals through an unfunded reward claim or pause/claim coupling. | **WAIT-ECON / WAIT-ADMIN.** Requires V1 withdrawal/reserve behavior and approved emergency policy. |
| ECON-07 — Total supply cannot increase after genesis under the fixed-supply model. | Assert each public and privileged path cannot mint after genesis. | Exercise token initialization, staking, claims, referrals, role assignment, and administrative flows; reconcile total supply. | Generate all permitted calls and roles; assert supply is constant after genesis. | Attempt mint through every role, upgraded implementation, referral path, and direct contract call. | **WAIT-ECON.** Fixed supply is preferred, but cap, genesis allocation, and post-genesis authority are undecided. | ECON-08 — Stake, reward, duration, referral, and rounding arithmetic stays within approved bounds and liability caps. | Boundary-test every approved minimum, maximum, rounding edge, and cap. | Combine maximum stake/duration/referral cases with reserve accounting and claims. | Fuzz approved parameter ranges against a separate reference model; assert exact or bounded agreement and no overflow. | Supply extreme values, near-overflow values, zero denominators, and malformed schedule inputs. | **WAIT-ECON.** Approved parameter ranges and reward formula do not exist. Legacy edge tests may remain characterization only. |
| ECON-09 — Existing positions retain their entry terms. | Store a position, change each permitted global setting, and compare effective terms. | Open multiple positions across versions/settings; verify prior positions retain original terms through maturity. | Generate settings changes and positions; assert each position's rate, maturity, principal, and entitlement remain fixed. | Attempt owner/admin mutation of existing positions and replay old configuration calls. | **WAIT-ADMIN / WAIT-IMPL.** Immutable-position principle is intended; permitted mutable settings and future position storage are not specified. |
| ECON-10 — Emergency pause blocks only approved operations and preserves eligible principal withdrawals and funded claims. | Test each method against the approved paused/unpaused access matrix. | Pause during active and matured positions; verify the approved withdrawal/claim behavior. | Generate pause/unpause and user actions; assert only listed operations are blocked. | Unauthorized pause/unpause, permanent-pause griefing, and attempts to freeze committed funds. | **WAIT-ADMIN.** Emergency powers and withdrawal policy remain open; current source exposes no public pause setter. |
| ECON-11 — Referral traversal is bounded, cycle-safe, and included in reward solvency. | Check eligibility, cycle rejection, maximum depth, and exact referral accounting. | Exercise chains at zero/one/maximum depth and concurrent referred positions. | Generate referral graphs; assert bounded traversal and reserve coverage for every accrued referral liability. | Long chains, cycles, self-referrals, referral reassignment, sybil-like repeated claims, and gas-limit pressure. | **HYBRID / WAIT-ECON.** Current two-account cycle check and legacy 1%/2% minting are characterized; V1 eligibility, depth, and funding are open. |

## Tests that can be implemented now

These tests observe existing code or security properties independent of the open tokenomics schedule. They must be named and reported as legacy characterization, never as V1 acceptance:

1. Reproduce the single-position escrow balance after stake and compare observed balances (`ECON-01` baseline only).
2. Run the duplicate legacy claim case under the epoch-aligned config and retain the default-clock pending status (`ECON-02` legacy only).
3. Keep authorized/unauthorized mint, operator, admin-role, and staking-wiring checks (`SEC-01` legacy access behavior).
4. Characterize current public stake amount/duration boundaries and owner setting behavior (`ECON-08`, `ECON-09` legacy behavior).
5. Characterize current referral reward amounts/cycle rejection and H-01/zero-denominator schedule failures (`ECON-11`, `SEC-06` legacy behavior).
6. Characterize current UUPS upgrade authorization, same-layout state retention, and standalone implementation initialization lockout (`SEC-03` legacy token behavior).
7. Extend the existing failed-allowance atomicity check to full state snapshots and add adversarial token doubles where the approved asset interface requires them (`ECON-12`, `SEC-04`, `SEC-09`).

Passing a characterization test can confirm existing behavior even when that behavior conflicts with V1 principles. Keep contradictory legacy tests as evidence; do not convert them into V1 acceptance tests by changing expected behavior before the owner schedule is approved.

## Tests gated on owner decisions or V1 implementation

- **Economic schedule:** ECON-03 through ECON-08 and ECON-11 need approved supply, rewards, rates, duration, amounts, referral rules, caps, rounding, reserve funding, and shortfall policies.
- **Administrative specification:** ECON-09/10 and SEC-01/02/08 need the approved governance identity, role matrix, mutable settings, timelocks, emergency powers, and withdrawal policy.
- **V1 implementation:** end-to-end acceptance for escrow-return lifecycle, reserve coverage, fixed supply, immutable terms, bounded referrals, and pause behavior must wait until a V1 implementation exists. Tests may be drafted as executable specifications but cannot be reported as passing against the legacy source.
- **Deployment:** network, chain ID, custody addresses, and transaction scenarios remain deferred to Phase 4; no deployment test or network selection is authorized by this matrix.
