### Follow-up implementation slice

`setMaxStakeDays` now rejects values below 2 with `Must allow at least two stake days.` This prevents setting zero days (which disables every stake) and avoids a zero denominator in `calcStakeShares` for a one-day maximum. `calcStakeShares` also validates its public duration input, so zero or above-maximum queries revert with `Invalid stake days.` instead of reaching arithmetic underflow or extrapolating beyond configured duration. `addDailyData` now rejects zero-share rows before they can become claim denominators. Staking uses `SafeERC20` and verifies the balance delta equals requested principal, rejecting false-returning and fee-on-transfer behavior without recording partial principal. `SynergiXToken` disables initializers on the standalone implementation while proxy initialization remains tested; direct implementation initialization now fails before roles can be assigned. Regressions cover each behavior. A test-only callback token confirms the staking reentrancy guard blocks nested `stakeStart` during `transferFrom` without breaking the outer stake. The README and package scripts now document the actual token-proxy/staking-constructor deployment shape, make the default deploy alias local-only, and remove the broken `npm run upgrade` alias to a nonexistent script. The proposed V1 docs now point to this current evidence without changing their approval gates. No deployment/upgrade was performed.

## Findings and disposition

- **H-01 remains open.** The epoch-aligned H-01 PoC confirms the current code applies Unix-day indexes directly to appended, zero-based `dailyData`. A correct day-to-row mapping, treatment of first/current/maturity days, missing records, cumulative-interest boundaries, initialization, and legacy rows requires an explicit schedule contract. The proposed documents do not approve those semantics. No fix or passing post-fix regression has been implemented.
- **Zero-share owner input is rejected for newly appended history.** Existing zero-share rows, if any, are unchanged and can still cause a claim revert; no recovery policy was selected because it could change accrued payout. The exact payout treatment for missing/current/maturity days and cumulative interest remains part of the unresolved H-01 schedule semantics.
- **`maxStakeDays` 0/1 setting and public share-calculation input faults are repaired and verified in the current worktree.** The setter enforces a minimum of 2 and `calcStakeShares` rejects durations outside `1..maxStakeDays`; the full suite and focused epoch-aligned suite pass. A deployed instance, if any, still needs verified state and compatibility review; this source change does not migrate it.
- **Stake amount, duration, bonus, burn, and mint/reward policy remain unresolved.** Current tests show the public token wrapper's exact 1,000,000-SNX range and the staking contract's unreachable 150,000,000-SNX bonus threshold; source constants are not approved product rules. No replacement values were invented.
- **Referral and active-stake loops remain unbounded.** The new local profile measures growth through 12 ancestry hops and 13 stake entries, while the existing referral test retains two-account cycle rejection. These measurements are not an exhaustion proof and do not establish a gas ceiling. A depth/stake-count bound affects eligibility; no approved bound exists, so adding an arbitrary cap could change product behavior.
- **Authorization/architecture still requires owner decisions and deployment facts.** The code combines `Ownable` and `AccessControl`; a new test confirms transferring staking ownership does not transfer `DEFAULT_ADMIN_ROLE`. Whether role transfer should follow ownership is a governance decision, not inferred here. The token is UUPS-upgradeable while staking is constructor-based. README and package metadata now match that architecture, but the deployment script leaves all initial authority with the deployer. No migration or deployment was performed.
- **Escrow, minting, reward solvency, referral funding, burn, and single-withdrawal policy cannot be resolved from legacy tests.** The approved architecture direction favors escrowed principal, separately funded rewards, and immutable V1, but exact economics, release design, and any migration are not approved. Do not reinterpret current mint-on-maturity behavior as an approved model.
- **Standalone UUPS implementation initialization is now disabled.** A regression confirms direct `initialize` reverts and proxy initialization plus authorized same-layout upgrade still work. This does not constitute a full storage-layout comparison across historical implementations or answer deployed proxy state.
